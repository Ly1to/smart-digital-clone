## 1. 文档目的

本文档用于明确个人日程系统第一版要解决的问题、包含的功能和验收标准。后续的页面原型、数据库设计、接口设计和开发排期都应以这里的范围作为基线。

第一版的目标是交付一个单用户、可以日常手动录入和管理日程的 MVP，优先保证日程能够按分类被可靠地创建、查看、修改和删除。第三方应用接入、消息导入和自动生成日程均不在本阶段范围内。

## 2. 产品定位

个人日程系统是一款以个人时间管理为核心的单用户 Web 应用，主要帮助用户：

- 在一个日历中集中管理个人日程
- 快速查看某一天、某一周或某个月的安排
- 将日程明确划分为工作、外出和私人时间三类
- 通过手动填写创建每一个日程
- 在不同设备上通过浏览器访问自己的日程

第一版不解决账号登录、多人用户、团队排期、会议室预订或内容协作问题。

> 当前实现已支持登录、注册与多账号数据隔离（每个账号只能看到自己的数据），但团队排期、会议室和协作仍不在范围内。

### 2.1 目标用户

第一版的目标用户就是项目所有者本人。系统围绕一个人日常的工作安排、外出活动和私人时间进行设计，不需要面向不同用户提供注册和登录能力。

### 2.2 产品假设

第一版按以下假设设计：

- 系统通过浏览器访问，优先适配桌面端，同时保证移动端可以正常操作
- 系统只服务一个用户，不提供注册、登录、退出和多用户权限功能
- 所有日程均由用户在前端手动填写并保存
- 每条日程必须归属于工作、外出或私人时间三个固定分类之一
- 第一版不接入 GitHub、音乐播放器、消息平台或其他第三方数据源
- 第一版不根据外部数据主动生成、推荐或导入日程
- 日期时间按浏览器或系统所在时区展示，暂不提供多用户时区配置

## 3. 第一版目标与非目标

### 3.1 第一版目标

- 基线：用户无需登录即可进入个人日历（现状：需要登录，首次部署创建管理员）
- 用户可以手动创建、查看、编辑和删除日程
- 用户创建日程时必须选择工作、外出或私人时间分类
- 用户可以通过分类颜色和筛选快速区分三类日程
- 用户可以按日、周、月查看日程
- 用户可以按标题、描述和分类查找日程
- 用户刷新或重新打开页面后，已创建的日程仍然存在

### 3.2 第一版非目标

以下能力不纳入 MVP（前两条已有变化）：

- 用户注册、登录、账号管理和多用户数据隔离（现状：已实现）
- 团队共享、多人编辑和权限管理
- 从 GitHub commit、本地音乐歌单或其他第三方应用自动生成日程（现状：GitHub / Gitee 更新会进入暂存区，确认后才写入日程）
- 接收邮件、聊天消息或系统通知并自动转换为日程
- Google Calendar、Outlook 等第三方日历双向同步
- AI 自动排期或自然语言创建日程
- 原生 Android、iOS 客户端
- 附件上传和复杂富文本编辑
- 会议室、资源和参与人管理
- 完整 iCalendar RRULE 编辑器
- 节假日、农历和特殊地区日历
- 离线编辑和跨设备实时冲突合并

## 5. MVP 功能范围

### 5.1 单用户模式（基线，已被多账号实现取代）

- 第一版不提供注册、登录、退出和密码管理
- 系统默认只有一个数据所有者
- 数据表和接口不设计用户归属、成员或权限关系
- 打开系统后直接进入日历主页
- 如果部署在公网，可以在反向代理或网络层增加访问保护，但这不属于第一版产品内的账号系统

### 5.2 日程分类

第一版采用三个固定分类，每条日程必须选择其中一个：

| 分类 | 标识建议 | 典型内容 |
| --- | --- | --- |
| 工作 | `work` | 工作任务、会议、截止事项、开发安排等手动录入的工作内容 |
| 外出 | `outing` | 旅游、约会、聚会、办事、出行等需要离开住所的安排 |
| 私人时间 | `private` | 听音乐、自主学习、运动、休息等个人安排 |

分类规则：

- 三个分类固定存在，MVP 不支持新增、删除或重命名分类
- 创建和编辑日程时必须选择一个分类
- 三类日程在日历中使用不同颜色区分
- 日历和列表中应显示分类名称或可识别的分类标识
- 用户可以按一个或多个分类筛选日程
- 分类只是日程属性，不替代标题；例如“晚上自主学习两小时”仍需填写标题

### 5.3 手动创建与日程管理

日程至少包含以下字段：

| 字段 | 要求 | 默认规则 |
| --- | --- | --- |
| 标题 | 必填 | 去除首尾空格后不能为空 |
| 分类 | 必填 | 工作、外出、私人时间三选一 |
| 描述 | 可选 | 支持普通多行文本 |
| 开始时间 | 必填 | 必须是有效日期时间 |
| 结束时间 | 必填 | 必须晚于开始时间 |
| 全天事件 | 可选 | 默认关闭 |
| 地点 | 可选 | 普通文本 |
| 状态 | 可选 | 默认为“待进行” |
| 标签 | 可选 | P1 能力，MVP 可以延后 |
| 提醒时间 | 可选 | P1 能力，MVP 默认不提醒 |
| 重复规则 | 可选 | P1 能力，MVP 默认不重复 |

状态建议先限定为：

- 待进行
- 已完成
- 已取消

日程操作要求：

- 可以从日历空白日期创建日程
- 可以点击已有日程查看详情
- 可以编辑日程标题、分类、描述、时间、地点和状态
- 删除前需要二次确认
- 保存失败时保留用户已经填写的内容并显示明确错误
- 所有日程内容必须由用户通过表单手动提交
- 第一版不提供批量导入、外部数据抓取、自动生成或自动补全日程
   > 现状：手动创建流程保持不变；GitHub / Gitee 数据只能经暂存区逐条确认后写入日程。

典型手动录入示例：

- 工作：添加“周五 14:00-15:00 项目周会”
- 外出：添加“周六 10:00-18:00 去附近城市旅行”
- 私人时间：添加“今天 16:00-17:00 听一小时音乐”
- 私人时间：添加“今天 20:00-22:00 自主学习”

### 5.4 日历视图

MVP 支持三种视图：

- 月视图：查看一个月内的日程分布
- 周视图：查看一周内各天的时间安排
- 日视图：查看一天内的详细时间安排

视图需要满足以下要求：

- 可以切换到前一天、后一天或当前日期
- 日程较多时可以在对应日期中看到摘要
- 跨天日程在涉及的日期中正确显示
- 全天事件和普通事件有明显区分
- 空日期和空列表需要显示友好的空状态

MVP 可以暂不支持拖拽修改时间，但页面结构不应阻止后续加入该能力。

### 5.5 搜索与筛选

第一版至少支持：

- 按标题和描述关键词搜索
- 按开始、结束时间范围筛选
- 按工作、外出、私人时间分类筛选
- 按状态筛选

可选支持：

- 快速清除全部筛选条件
- 保存最近一次视图和筛选条件

### 5.6 日期时间

- 数据库统一保存 UTC 时间，避免后续迁移时出现时间偏移
- 接口传输 ISO 8601 时间字符串
- 前端默认按照浏览器或系统所在时区展示日期和时间
- 第一版不提供多用户时区设置
   > 现状：界面仍按浏览器本地时区展示；后端自动排程窗口由部署级 `APP_TIMEZONE` 决定。
- 需要正确处理全天事件、跨天事件和本地日期边界

### 5.7 后续能力

以下能力可以在 MVP 稳定后逐步加入，但不阻塞手动创建流程的交付：

- 开始前提醒
- 每日、每周、每月重复
- 自定义标签
- ICS 导入导出
- 日程冲突提示
- 自然语言快速录入

GitHub commit、本地音乐歌单、邮件、聊天消息等第三方数据接入需要单独进行需求设计，不纳入第一版。

## 6. 核心业务规则

1. 标题不能为空，描述可以为空。
2. 每条日程必须属于工作、外出、私人时间之一。
3. 第一版只允许使用三个固定分类，不提供分类管理功能。
4. 普通日程的结束时间必须晚于开始时间。
5. 全天事件的开始日期和结束日期都包含在日程范围内。
6. 跨越零点的日程必须在涉及的日期中正确展示。
7. 数据库保存 UTC 时间，前端按浏览器本地时区展示，不改变原始时间点。
8. 所有日程必须由用户手动填写和提交，不根据外部数据自动创建。
   > 现状：自动来源只生成待确认条目，仍需用户确认后写入日程。
9. 无需账号即可使用，不在业务数据中引入用户或成员关系。
   > 当前实现已引入 `users` 表、`user_id` 归属和 JWT 登录，本条仅描述最初 MVP。
10. 后端返回统一、可理解的错误信息，前端负责展示表单和接口错误。
11. 提醒、重复规则和第三方数据接入不参与 MVP 的核心创建流程。

## 7. 页面范围

第一版包含以下页面：

| 页面 | 主要内容 |
| --- | --- |
| 登录页 | 登录、首次创建管理员账号，入口进入注册页 |
| 注册页 | 创建新账号（可通过 `ALLOW_REGISTRATION` 关闭） |
| 日历主页 | 日/周/月视图切换、日期导航、创建入口、暂存区入口 |
| 日程详情 | 查看完整日程，进入编辑或删除 |
| 日程创建 | 手动填写标题、分类、描述、时间和地点 |
| 日程编辑 | 修改已有日程的手动填写内容 |
| 搜索筛选 | 关键词、日期范围、分类和状态筛选 |

页面应具备加载、空数据、成功和失败状态。移动端至少保证可以查看日程、手动创建日程和编辑日程。

## 8. 验收标准

| 编号 | 验收场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 登录后使用（基线为免登录） | 未登录时跳转登录页；首次部署引导创建管理员账号；登录后进入日历 |
| AC-02 | 手动创建日程 | 合法日程保存成功，刷新页面后仍能查询到 |
| AC-03 | 分类必填 | 未选择分类时不能保存；合法分类可以正常保存和展示 |
| AC-04 | 分类识别 | 工作、外出、私人时间使用不同颜色，并且容易辨认 |
| AC-05 | 非法时间 | 结束时间不晚于开始时间时不能保存，并显示错误 |
| AC-06 | 编辑和删除 | 修改后数据正确更新；删除后不再出现在日历中 |
| AC-07 | 切换日历视图 | 日、周、月视图都能显示同一时间段内的正确日程 |
| AC-08 | 分类筛选 | 选择一个或多个分类后，只显示对应分类的日程 |
| AC-09 | 搜索和日期筛选 | 标题、描述、日期范围和条件组合能得到正确结果 |
| AC-10 | 跨天和全天日程 | 在涉及的日期中正确显示，时间逻辑符合业务规则 |
| AC-11 | 本地时间展示 | 保存后按当前浏览器时区展示为正确日期和时间 |
| AC-12 | 手动录入边界 | 手动创建流程不依赖外部导入；GitHub / Gitee 数据只能经暂存区确认后进入日历 |
| AC-13 | 移动端操作 | 可以查看、手动创建和编辑日程，表单内容可正常显示 |

## 9. MVP 完成标准

满足以下条件后，第一版才可以进入部署和试用：

- 所有 P0 用户故事完成
- 所有验收标准通过自动化测试或明确的人工验证（已由 `make verify` 覆盖）
- 核心日程操作可以在桌面端和移动端浏览器完成
- 工作、外出、私人时间三类日程可以创建、展示和筛选
- 手动创建流程不依赖外部导入；第三方来源只能经暂存区确认后写入日程
- 数据库迁移可以重复执行，并能从空数据库完成初始化
- 至少连续试用一周，没有出现数据丢失或分类错误
- 如需公网部署，访问入口具备基本保护

## 10. 已确认的产品决策

| 决策项 | 第一版决策 | 影响 |
| --- | --- | --- |
| 用户模式 | 基线：单用户，不提供登录和账号管理；现状：多账号登录与数据隔离 | 认证、权限和用户数据隔离已落地 |
| 日程分类 | 固定为工作、外出、私人时间 | 数据模型只需保存固定分类值 |
| 日程来源 | 第一版全部由用户手动创建和编辑 | 不设计导入、抓取、消息队列和自动生成流程 |
| 第三方接入 | 基线：不接入 GitHub、音乐平台、邮件或聊天消息；现状：已接入 GitHub / Gitee 自动来源暂存区 | 暂存区与同步服务已落地，第三方日历同步仍未做 |
| 提醒 | 放到 P1 | MVP 不需要定时任务和通知基础设施 |
| 重复日程 | 放到 P1 | MVP 按单次日程保存 |
| 标签 | 放到 P1 | MVP 使用固定分类完成主要区分 |
| 自定义分类 | 放到 P2 | 避免增加分类管理页面和数据关系 |
| 拖拽修改时间 | 放到 P1 | 减少 FullCalendar 交互和测试工作 |
| 日程冲突检测 | 放到 P2 | 不阻塞基础日程管理 |
| ICS 导入导出 | 放到 P1 | 不阻塞手动创建流程 |

以上决策作为后续原型、数据库和接口设计的第一版基线。如果范围发生变化，需要先更新本文档。
