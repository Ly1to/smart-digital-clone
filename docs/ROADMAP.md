## 2. 下一步（P1）

### 2.1 QQ 机器人 Phase 3：写操作

- 新增工具：`create_schedule`、`update_schedule_status`、`delete_schedule`
- 两阶段确认：模型生成提议 → 用户回复“确认” → 后端执行
- 删除必须二次确认；写操作记录日志
- 每个 QQ 的频率限制（例如每分钟 N 次、每天 M 次）
- 验收：未确认不落库；越权返回 404；重复确认不会重复创建

### 2.2 QQ 机器人 Phase 4：前端与部署

- 前端账号区域：生成绑定码、展示绑定列表、解绑、显示连接状态
- Docker Compose 可选 `napcat` 服务（profile，默认不启动）
- 部署文档补充 QQ 风控、Token 成本、故障恢复
- 验收：不通过 Swagger 也能完成绑定/解绑；容器内可直连 NapCat

### 2.3 提醒

- 新增 `reminders` 表或 `schedules.remind_minutes`
- 单实例使用 APScheduler；重启后恢复任务
- 先做站内提醒，再评估 Web Push/邮件
- 验收：同一提醒只发送一次；服务重启后仍能触发

### 2.4 重复日程

- 使用 RRULE 字符串，服务层展开实例
- 支持每天/每周/每月，先不做复杂例外
- 验收：展开后的实例可查询、编辑单次实例不破坏规则

### 2.5 标签与 ICS

- 标签：`tags` + `schedule_tags`，筛选与表单
- ICS：导入/导出单次日程与全天事件
- 验收：导出的 ICS 可被 Google Calendar/Outlook 正确导入

## 4. 已知限制

| 限制 | 影响 | 缓解 |
| --- | --- | --- |
| SQLite 单写者 | 高并发写入会排队 | 当前规模足够；后续迁 PostgreSQL |
| 单进程 bot | 多 worker 会重复回复 | 只运行一个 worker；后续拆 bot worker |
| 绑定码在内存 | 重启后失效 | 10 分钟有效期，重新生成即可 |
| QQ 协议非官方 | NapCat/Lagrange 可能触发风控 | 小号、控制频率、关注社区动态 |
| 对话历史在内存 | 重启丢失上下文 | 当前可接受；Phase 3 评估持久化 |
| 无真实 QQ 端到端测试 | 联调风险 | 首次部署按 DEPLOYMENT 手工验收 |
| 无速率限制 | 可能被刷 Token | Phase 3 增加每 QQ 限额 |
| 前端无绑定 UI | 绑定需用 API | Phase 4 补齐 |

## 5. 设计决策记录

| 日期 | 决策 | 理由 |

| 2026-11-04 | Vue 3 + FastAPI + SQLite | 个人规模、开发效率、部署简单 |

| 2026-11-20 | 只读优先 | 先验证对话质量，再开放写操作 |
